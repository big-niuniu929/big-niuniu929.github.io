01 /

问题

改简历的默认动作是润色：把句子改漂亮，把动词换强，把「参与」换成「主导」。但面试官不按润色后的句子问，他挑一句追问：这件事你到底做了什么，数据哪来的，为什么是你。

我帮同学改简历时，真正花时间的不是改词，是逐句问「这条有证据吗」。有些句子一问就塌：项目是团队做的，简历写成一个人干的；数字是拍脑袋写的，追问来源就卡住。

所以我把工具的方向定在「先找会被追问的地方」，而不是「先帮你写得更好看」。诊断在前，改写在后面；没有证据的地方，工具应该先让它露出来，而不是替你把话编圆。

需求来自我自己和身边同学，没有做过市场验证。这一点决定了后面的商业化判断，我放在最后一节说。

02 /

约束

能做成什么样，先被四个条件框住。

时间

从项目计划书到发布准备，中间还做了一版下一代重构。重构没有上线，所以对外只算一条产品线，不把两代拆成两个项目。

人力

一个人，加 AI 协作开发。我是产品负责人，代码由 AI 协作产出，我定规则、审结果、跑流程。这个分工要写在前面，否则「13,611 行」实测 很容易被读成一个人逐行敲出来的。

数据

测试期数据库里攒过同学的真实简历，可能含姓名、学校、电话。发布前必须清空，数据库文件不进任何仓库。这条是隐私红线，不是可选项。

环境

单文件 Python 服务，只用标准库，不装第三方包；一台小机器部署到公网。规则引擎模式不配置 API Key 也能跑，这是它现在能公开试玩的原因。

03 /

我的角色

我做了什么

产品定义、规则与知识库口径、商业机制设计、前后端实现与公网部署。具体是三件事：把「会被追问」拆成可检查的规则；给每条经历挂证据字段，改写结果做数字防新增校验；把定价、会员、额度扣减、风控和后台毛利核算做出来。

发布前我还做了一次「未通电」自查。自查清单上的每一项都不好看，但它是这个项目里最有用的一份文件。

我没做什么

代码是 AI 协作产出的，我是产品负责人，不是逐行手写的那个人。这句话不能省，因为「13,611 行」实测 这个数字本身不说明谁写的。

我没有拿到一个付费用户，没有做真实推广。AI 那条路径也从没被真实调用过——线上跑的是规则引擎模式，它不依赖任何 Key。

公网能打开、流程能走完，不等于上线运营。它现在是 L2：能证明「这条流程成立」，不能证明「有人愿意为它付钱」。

04 /

方案与取舍

这个产品的定位不是「帮你写简历」，是「先告诉你哪里会被问穿」。普通简历优化工具从「怎么写得更强」出发，优化措辞和排版；我从「哪句话经不起追问」出发，把简历当成一个会被攻击的靶子，先诊断，再决定改不改、怎么补证据。

这个角度和普通工具的区别在顺序上：普通工具先给你一个更好的版本，再让你自己判断能不能用；这个工具先给你一份问题清单，告诉你哪句会被追问、缺什么证据，然后才谈改写。

  1. 按岗位族和关键词读简历，定位每一句在说什么：是职责、是结果，还是自我评价。
  2. 给每一句挂可攻击点：数字有没有来源、角色是不是被夸大、结果能不能归因到你、时间线对不对得上。
  3. 生成追问清单：这题考什么、按 STAR 你缺哪一块、常见坑是什么。改写建议只在有证据时给，没证据的先标出来让你补。
我放弃了什么

放弃一键美化。那个方向更好卖，点一下就能看到一张更漂亮的简历；但它会把没有证据的句子写得更像真的。

放弃让 AI 当主路径。规则引擎是主路径，AI 只是可选增量。代价是产品看起来不够「AI」，收益是断网、没有 Key 也能用，而且每条判断都能解释。

还放弃了先做增长。我把商业机制做完了才去找用户，顺序反了——这条放在最后一节。

停掉的姊妹形态

简核最早还有一个姊妹形态：给一段 JD 自动出题、分维度打分，每个分数都挂回你说过的原话。那个形态后来停掉了。停掉的原因不是做不出来，是我发现它解决的是「面试练得像不像」，而真正卡住人的是「简历里这句会被追问什么、你答不上来」。练得再像，简历里那句撑不住的话还在。

判断方式我留了下来，用到了简历上：每一处改写建议，都要能指回原文的哪一句、追问会从哪来。这条约束后来成了简核的主干。

05 /

最难的一个点

最难的不是把功能做出来，是我在计划书里写「已具备完整商业机制」的时候，机器其实没转过。

发布前自查才发现：定价、会员、额度、风控都在，注册和付费是空的；AI 那条路径从没被真实调用，线上跑的是规则引擎模式；版本管理做了，但从没被真实使用过。功能清单是满的，使用记录是空的。

我把对外口径全部改成「0 付费用户」实测，把「未通电」写进交接文档的风险项，并在发布前清空测试库里的简历档案。这三件事都不难，难的是承认前面那个「完整」是设计上的完整，不是运行过的完整。

那次自查之后，我对「做完了」这三个字谨慎了很多。现在每做一块功能，我都会先问一句：它被真实调用过一次吗？如果没有，它就不能算完成，只能算写好了。

这一节真正学到的

机制完整不等于产品成立。能证明「我设计过」的东西，不能拿去证明「有人要」。

结果

08 /

我做错了什么 / 如果重做

三个问题，按难受程度排。

  1. 我把商业机制做得比用户更完整。定价、会员、额度、风控全部实现，一个付费用户都没有。这是「先做机制、后找需求」的典型错误。机制越完整，越容易让自己相信「产品快好了」。
  2. 发布时整个产品是「未通电」的。计划书里写「已具备完整商业机制」，但注册和付费是空的，AI 路径从未真实调用。发布前自查才把这句改掉。
  3. 测试期数据库里躺着同学的简历档案，可能含姓名、学校、电话。发布前必须清空，数据库文件不能进仓库；Git 历史删不干净，所以宁可重建仓库。

如果重做会怎么做

  • 先找真实求职者，用他们的简历跑诊断，记录他们改了什么、有没有回来用第二次；再决定要不要做定价。
  • 商业机制先做最小一版：一个价格、一次收款、一笔对账。跑通一次真实收款，再扩会员和额度。
  • 上线前先写「这台机器现在能证明什么、不能证明什么」，把不能证明的写在首页，而不是等别人问。
  • 数据库从第一天就用合成数据，真实简历只在本地内存里过一遍，不落库。
  • 把「有没有被真实调用过」做成发布门槛。没有调用记录的功能，一律标成「写好了，没验证」。
